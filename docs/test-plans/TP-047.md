## Driver

1. **The notice.** Below each flagged answer, the notice listed every unverified number and its reason, for example "unverified (this price change belongs to 0700.HK; marked [?]): -6.0993, 3.1153". After three flagged answers in a row, it added "three answers in a row contained unverified numbers; check the data". In live use the list read as an accusation against the answer, and after a false flag it pushed the model into retracting correct numbers (BD-035). The owner wants one fixed sentence.

   REQ-SI-INV-001 says the user "is told which values are unverified and why", so this is a requirement change, not a display tweak. The `[?]` marker stays on every unverified number, which still tells the user which values are unverified. The reasons stay in the session record (`unverified_detail`), the post-check is unchanged, and the model's own feedback ("[harness] The numbers marked [?] were not verified ...") is unchanged.
2. **Freshness.** The real store was a month stale on 2026-11-03 until a manual sync, and stale answers are correct against the stored data but out of date. The owner wants every start to check the data against today and sync when it is behind.

## Design

### Notice (`agent/loop.py`; not a gated path)
- A flagged answer is followed by the fixed line `data with [?] means the data may be fabricated`, shown once per answer. No numbers and no reasons are shown.
- The three-in-a-row notice is no longer shown. `PostCheckCounter` keeps counting, because the INV-002 abort budget lives in the same counter.
- Unchanged:
  - the guardrail (`agent/guardrail*`), so the constants stay unused in the display;
  - the `[?]` marks, the stored `unverified`, `original` and `unverified_detail` fields, and `show`;
  - the `/report` header count required by FR-008.

### Freshness check (`data/ingest/freshness.py`, exposed through the data facade)
- **Expected session for an exchange.** It is the latest weekday whose end-of-day bar is reliably at the vendor by `now`. That time is close plus a margin, in UTC: HK 10:00 (close 08:00 UTC), US 23:00 (close 20:00 or 21:00 UTC, depending on daylight saving).
- **Tracked symbols.** The four benchmark indices and the active watchlist. Each is mapped to HK or US by the existing `_calendar_exchange`.
- **When a symbol is behind.** A symbol is behind when its newest stored bar is older than its exchange's expected session, and its market track has not run since that session became available.

  The second condition makes the check safe on holidays. A sync after the holiday's availability time returns no new session, so the check does not fire again until the next weekday.
- **Output.** `DataStore.freshness(now=None)` returns the behind symbols (symbol, newest bar, expected session) and whether the market source is configured.

### Startup sync (`cli/app.py`)
- **When it runs.** Interactive sessions (bare `stockinsider`, `analyze`, `resume`, under either front-end) and `digest` call the check before opening a session.
- **When something is behind.**
  - The CLI prints `data is behind (<n> symbol(s), e.g. <symbol> through <date>, expected <date>); running sync (skip with --no-sync)`.
  - It runs the same code as `stockinsider sync`, which is moved into a shared helper, then the same code as `stockinsider embed`.
  - A sync or embed failure is reported and the session still starts. The data then stays as it is, and every answer keeps its as-of dates (INV-003, runtime policy P-03).
- **Without a market key.** Nothing is fetched. The CLI prints one line saying the data is behind and that sync needs `EODHD_API_KEY`.
- **Without an embedding provider.** The embed step is skipped, with one line saying so.
- **Opting out.** `--no-sync` on each of these commands, or `STOCKINSIDER_NO_SYNC=1`, skips the check.

## Planned tests

New file `test/offline/test_tp047_notice_and_freshness.py`.

| Test | Verifies | Kind |
|---|---|---|
| `test_flagged_answer_shows_only_the_fixed_notice` | a fabricated number is marked `[?]`, and the progress channel shows the fixed line and no number or reason | positive + negative |
| `test_reasons_stay_in_the_record` | the stored assistant message still carries `unverified` and `unverified_detail` with reasons | positive |
| `test_verified_answer_shows_no_notice` | a correct answer prints no notice line | negative |
| `test_no_streak_notice_after_three_flagged_answers` | three flagged answers in a row print no "in a row" line | negative |
| `test_expected_session_by_exchange_and_time` | before and after the availability time; Saturday, Sunday and Monday morning map to the previous Friday | boundary (±1) |
| `test_behind_when_bar_older_and_no_run_since` | a symbol with an old bar and an old run is behind | positive |
| `test_not_behind_after_a_run_since_availability` | an old bar but a run after availability (holiday) is not behind | negative |
| `test_not_behind_when_bar_is_current` | the newest bar equals the expected session | negative |
| `test_startup_runs_sync_and_embed_when_behind` | `analyze` with a behind store runs the sync helper, then the embed helper, then opens the session | positive |
| `test_startup_skips_when_fresh` | a fresh store runs no sync | negative |
| `test_no_sync_flag_and_env_skip` | `--no-sync` and `STOCKINSIDER_NO_SYNC=1` skip the check | negative |
| `test_startup_without_market_key_fetches_nothing` | no key: one line, no sync call, the session opens | negative (INV-003) |
| `test_sync_failure_still_opens_session` | a raising sync is reported and the session opens | adversarial |
| `test_digest_runs_the_check` | `digest` runs the same check | positive |

Mutation checks: the availability time, the "run since availability" condition, the startup call, and the notice text.
