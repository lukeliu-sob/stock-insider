## Driver

DE-15 (field/subject typing in `agent/guardrail_claims.py` is a hand-maintained cue vocabulary guessing at tool-result meaning) and DE-16 (company names resolve only when the session ledger happens to carry one) are both named in ADR-008 as deferred to "phase 3." ADR-005 Amendment 4 records the wire-format decision this plan implements: `ToolSpec` gains `result_fields`/`result_discriminators` (a `FieldSemantics` declaration per field, direct or discriminator-tagged), and `official_name` reaches the tools DE-16 names. See that amendment for the alternatives considered (full jsonschema/pydantic adoption, rejected as oversized) and the residual risk this plan does not close (a company entirely absent from a session's ledger still cannot be recognized as a subject).

## Scope, staged (TP-017 PR-1..3b precedent: one plan, several PRs)

- **Stage 1 (this PR)**: the contract only. `shared/tools.py` gains `FieldSemantics` and the two new `ToolSpec` fields, defaulting to empty - every existing `ToolSpec` is unaffected, nothing declares anything yet, nothing consumes it. Zero behavior change; purely additive.
- **Stage 2**: `agent/guardrail_claims.py`'s evidence-typing (`_evidence_field`, `index_evidence`) reads a tool's declared `result_fields`/`result_discriminators` when present, falling back to the current heuristic vocabulary otherwise - the cutover is per-tool, not a single flag day. Requires a way for the guardrail to look up a tool's `ToolSpec` by name (`agent/guardrail_claims.py -> agent/registry` is an allowed edge per AGENTS.md's dependency map; exact accessor shape decided when this stage is scoped).
- **Stage 3**: declare `result_fields`/`result_discriminators` for the data modules currently read by the heuristic vocabulary, in small batches (`market.py` + `fundamentals.py`; then `indicators.py`; then `news.py` + `eodnews.py` + `sync.py` + `watchlist.py` + `resolver.py` + the `store/__init__.py` facade) - each batch independently testable, each batch's tools stop relying on the fallback.
- **Stage 4 (DE-16)**: `official_name` added to `market.quote`, `market.indicators`, `fundamentals.summary`, `news.recent`, `news.search` (joining the symbols table `resolver.py` already populates); `agent/guardrail_claims.py`'s subject resolution reads it as a fourth source alongside tickers, bare codes, and the first word of an existing `official_name`.
- **Stage 5**: P6 held-out remeasurement (a fresh battery, not E-010 reused, since the typing mechanism itself changed - same discipline TP-024 used), recorded as ADR-008's own phase-3 amendment once stages 2-4 are in.

Each stage amends this plan's "Planned tests" and "Regression scope" before its own implementation commit (GOV-006); stage 1 below is fully scoped now.

## Stage 1: scope, fix, and tests

**Fix**: `shared/tools.py` adds the frozen `FieldSemantics` dataclass (`field: str`, `unit: str = ""`, `subject_bearing: bool = False`) and two new `ToolSpec` fields (`result_fields: dict[str, FieldSemantics] = field(default_factory=dict)`, `result_discriminators: dict[str, dict[str, FieldSemantics]] = field(default_factory=dict)`). No other file changes - no tool declares either field yet, `registry.py`'s `Registry.execute()` is untouched (ADR-005 Am4: this is declared metadata for the guardrail to consume later, not a new registry enforcement point).

In scope (files): `src/stockinsider/shared/tools.py`; new assertions in `test/offline/test_inv3_failsafe.py` (ADR-005 §3 names it "the growing home" for the fail-closed wire matrix `ToolSpec`/`validate_result_payload` already live in).

Explicitly NOT changed in stage 1: `agent/registry.py`, `agent/guardrail_claims.py`, every data module, `official_name` anywhere. No tool's `ToolSpec` literal gains either new field yet.

| Test | Verifies | Kind |
|---|---|---|
| `test_field_semantics_is_a_frozen_value_type` | the new dataclass is immutable and equality-comparable, matching every other wire type in the file | positive |
| `test_toolspec_defaults_are_empty_and_backward_compatible` | every existing `ToolSpec(...)` construction (no new arguments) still produces `result_fields == {}` and `result_discriminators == {}` | positive — regression guard |
| `test_declaring_result_fields_does_not_change_validation` | a `ToolSpec` built with a populated `result_fields`/`result_discriminators` still passes `validate_result_payload` exactly as an undeclared one does - the new fields are inert to the existing wire checks | negative/adversarial (R7): proves stage 1 cannot silently start enforcing something |

## Fit-criteria mapping (stage 1)

REQ-SI-INV-001/SEC-002: unchanged scope - stage 1 adds no new verification behavior, it adds the vocabulary stage 2 will verify against. Fit criterion is purely structural: the new type exists, is wired into `ToolSpec`, and changes nothing observable yet.
