## Driver

In the smoke test, the owner asked "How has Tencent traded over the last month, and how does that compare with the Hang Seng Index?" The model answered that it could not: no tool returns more than the latest bar, so a one-month move is out of its reach, although `stockinsider info` computes the same 20-session move deterministically on the data side. The model also met a raw Python error type: an absent symbol fails `market.quote` with `KeyError: '0700.HK: no stored market data ...'`, where the quotes come from `KeyError`'s own `repr`.

## Scope

- `data/compute/compute.py`: `period_performance(bars, windows)`. For each trailing window (5, 20, 60 and 250 sessions), the row carries the two dates, the two adjusted closes, and the percent change rounded to four decimals. A window the stored history cannot cover, or whose base close is zero, goes to `unavailable` with its reason (INV-003).
- `data/store/__init__.py`: `DataStore.market_performance(symbol)` reads the latest 251 adjusted closes and calls the compute function. A symbol with no bars raises `LookupError`. The same change applies to the existing no-data `KeyError` in `market_indicators_snapshot`.
- `agent/registry.py`: a new registration function, `register_performance_tools`, registers `market.performance` (READ, COMPUTED, argument `symbol`, result `dict` with `official_name` as the other market tools). It sits in its own function because the TP-025 stage-3 tests pin the tool count and the declaring set of the existing registration functions; those stay valid. The tool declares no result fields: the heuristic types `sessions` and `adjusted_close` by key, and leaves `change_pct` and `from_adjusted_close` `unknown`. A signed claim such as "-2.73%" verifies against them under the existing rules (probe below). The no-data raises in `market.quote` and `news.recent` become `LookupError`.
- `agent/repl.py`: `build_registry` calls `register_performance_tools` with the data store.
- Not changed: `shared/`, `agent/guardrail*`, `prompts/`, the specs and results of the existing tools.

Probe on the unchanged post-check, over a result of this shape: "-2.73%" in prose or in a table verifies (rounded); "20 sessions" and "5 sessions" verify as session counts; "fell 2.73% over the last 20 sessions" does not, because the decline word is read as the sign of "20". That is a claim-side reading error. It belongs to the post-check follow-up plan, not here.

## Planned tests

New file `test/offline/test_tp041_performance_tool.py`.

| Test | Verifies | Kind |
|---|---|---|
| `test_period_performance_rows` | 30 bars: the 5- and 20-session rows match hand-computed changes; 60 and 250 are unavailable with the stored count in the reason | positive + negative |
| `test_period_performance_zero_base_is_unavailable` | a zero base close puts the window in `unavailable` with the InvalidInput reason | negative |
| `test_market_performance_tool_result` | the registry tool returns the symbol, the windows, `unavailable`, `official_name`, and COMPUTED provenance | positive |
| `test_market_performance_unknown_symbol_fails_closed` | no bars: `ok` false, error names `LookupError` and the no-data reason, no `KeyError` repr quotes | negative/adversarial |
| `test_market_quote_no_data_error_is_clean` | the same for `market.quote` | negative |
| `test_signed_performance_claims_verify` | "-2.73%" (prose and table) and "20 sessions" verify against the tool's result; "-3.5%" is flagged | positive + negative |
| `test_build_registry_exposes_market_performance` | the REPL registry lists the tool when a data store is present, and not without one | positive + negative |

Mutation checks: drop the `unavailable` branch (a short history then raises or fabricates); compute the change against the wrong base bar.
