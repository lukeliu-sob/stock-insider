## Driver

TP-036 measured relevance@5 = 0.768 against the 0.8 QA-002 threshold
(E-011, DE-17); hit@5 = 0.920 passes. Owner decision (2026-10-26):
try a retrieval improvement under its own plan. The D1 v2
precondition, and with it TP-035, waits on the result.

## Overfitting guard (first commit, before any experiment)

The 25 TP-036 queries have now been looked at, so they become the
**development set**. Before any candidate is measured, a **held-out
query set** (`retrieval_queries_heldout_v1.json`, at least 20
queries, the same five classes and the same family rule) is written
and committed. Its labels are fixed in that commit. The gate decision
uses the held-out set; the development set is reported alongside.
This is the DE-09 lesson: a set tuned against cannot also certify.

Author separation (owner decision, 2026-10-26): the held-out set is
written by a separately briefed subagent that sees only the corpus,
the family partition, the query classes and the labeling rule. It does
not see the variants, the development queries or the E-011 results.
The main session checks it for integrity and overlap with the
development set, and does not edit its queries or labels.

## Stage 1 — offline experiment (test-only, no `src/` change)

Each candidate gets its own frozen vector file from the live
generator (extended with a `--variant` option); the offline harness
measures every variant on both sets.

| Variant | Change | Where it would land |
|---|---|---|
| V0 baseline | title only, raw query (E-011) | — |
| V1 query instruction | queries embedded with a retrieval instruction prefix (asymmetric retrieval; supported by Qwen embedding models) | query path of `news.search` (`agent/registry`) or the provider layer |
| V2 entity expansion | query expanded with the symbol map's official name and aliases when a watchlist ticker or alias matches (WeChat → Tencent) | data facade, deterministic |
| V3 V1 + V2 | both | both |

Rules: variants are fixed in this plan before measurement; no
per-query tuning; the instruction text is written once and logged.

### Variant definitions (fixed 2026-10-26, before any variant vector)

Code: `test/offline/retrieval_variants.py`, shared by the generator and
the suite; every embedded string is hash-checked.

- **V1**: `"Instruct: <task>\nQuery: <query>"` with the task text
  "Given a financial news search query, retrieve news headlines that
  are relevant to the query". Corpus titles are embedded unchanged.
- **V2**: production-shaped symbol map. For stocks resolved through the
  vendor search, production stores the canonical symbol and the
  vendor's official name, and no aliases; only the benchmark indices
  carry aliases. A query matches an entity on its ticker code
  (case-sensitive, word-bounded, the S2 rule), on the first word of its
  official name, or on an alias (case-insensitive, word-bounded). Each
  matched entity appends "<official name> (<code>)" to the query. No
  brand or product aliases are added (for example no WeChat → Tencent),
  because production has no source for them.
- **V3**: V1 applied to the V2 text.
- Corpus vectors: the TP-036 frozen title vectors are reused unchanged
  (same model id); only query vectors are generated per variant.

### Held-out set check (2026-10-26, before measurement)

The subagent's set has 25 queries, 5 per class, and all 12 families
are covered. Every target is in its family. Two queries have exactly
the same text as development queries (held-out 11 and 17); the author
had not seen the development set. Fixed rule: certification uses all
25 held-out queries, and the 23-query subset without the two exact
duplicates is reported alongside. Neither the queries nor their labels
are edited.
Each variant's scores go to an evaluation logbook entry (E-012).

## Stage 2 — implement the winner (separate PR, after the owner picks)

- The owner picks a variant from E-012 (or stops).
- If the winner touches `news.search` in `agent/registry`, that change
  needs an ADR-005 amendment and explicit approval (safety-critical
  path); if it touches only the provider layer or the data facade, it
  follows the normal gate.
- Indexed vectors: V1 changes only query vectors; V2 changes only
  queries. Neither needs a re-index of stored title vectors.
- Acceptance: relevance@5 >= 0.8 and hit@5 >= 0.8 on the held-out set
  with the production code path. On a pass, the strict expected
  failure in `test_retrieval.py` is removed on purpose and DE-17
  closes; the D1 v2 precondition is then met.
- On a miss: no threshold lowered, no label changed; owner decision
  (stop and accept the residual, or a further plan).

## Stage 1 result (2026-10-26, E-012)

| Variant | Held-out relevance@5 | Held-out hit@5 |
|---|---|---|
| V0 baseline | 0.720 | 1.000 |
| V1 query instruction | 0.712 | 1.000 |
| V2 entity expansion | 0.736 | 1.000 |
| V3 both | 0.728 | 1.000 |

No variant reaches the 0.8 threshold on the held-out set. V3 leads on
the development set (0.784) but not on the held-out set, so tuning
gains there would not certify. Stage 2 awaits the owner's choice
among: stop and accept the residual for D1 v2; adopt V2 for its small
gain without closing DE-17; or a further plan that works on the
corpus side rather than the query side. The random-vector control
stays in `test_retrieval.py` (it does not depend on the variant).

**Stage 2 decision (owner, 2026-10-26)**: stop; no variant is
adopted. The residual is accepted for D1 v2 (design decision D10a),
QA-002 stays unmet (DE-17), and it is re-measured when body-inclusive
embedding is decided. No stage-2 code change follows from this plan.
