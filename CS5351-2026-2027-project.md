## 1. Project Overview

Your team will design, build, and maintain a software application that contains an AI component, using an AI coding agent under human supervision. The project applies the full software engineering lifecycle taught in this course: you will specify requirements in machine-readable form, produce architecture artifacts that constrain what the coding agent may and may not do, govern the agent's code generation and verification, and demonstrate that you can review, debug, and maintain AI-generated code.

Your application is your own choice — it must contain at least one genuine AI component (an LLMpowered feature, a retrieval/augmentation pipeline, an AI-assisted decision path, etc.) and at least one safety-relevant boundary where the AI's output must be constrained by deterministic code. The reference implementation shown in lectures (VHIS) is a pattern to follow, not a project to extend.

## 2. Team Composition and Role Assignment

Your team should rotate roles so that students can experience different responsibilities in producing software using an AI coding agent, project management, or software engineering processes.

## 3. Deliverables

## D1 — Requirements (machine-readable)

Produce a machine-readable product requirements document and a consolidated requirements registry, both in YAML, under `./docs/req/` where `.` is the project root.

`docs/req/requirements.yaml` — every requirement as an entry with an ID, type, statement, and a machine-checkable fit criterion, plus priority. Types cover functional behavior, invariants (nonnegotiable rules with zero-tolerance fit criteria), quality attributes, performance, cost, governance, and security. Non-functional requirements are expressed as metric + threshold + verification. Prioritization uses MoSCoW, and states the tradeoff explicitly. Requirements discovered through analysis of any existing system or repository are included and linked to their sources.

• `docs/req/req-schema.json` — the schema used by CI in GitHub to validate the registry as a date.

## D2 — Architecture Artifacts (all as markdown .md files)

Produce the architecture documentation as a single artifact per file in `./docs/architecture/`, with `.` as the project root.

1. Architecture blueprint — the master constraint document that the Plan agent reads: scope, architectural drivers, system boundaries, components, authority boundaries (what is advisory vs authoritative), agent workflow, permissions, verification strategy, observability, and change policy.

2. Architecture Decision Record — the chosen architecture, the alternatives considered, the rationale, consequences, and conditions that would reopen the decision. It should also present the architectural design process. In addition, for your AI component, present your designed layered context structure that the AI receives on every turn (e.g., identity, standing constraints, retrieved knowledge, conversation history, resumable state, and the current task), the assembly pipeline (e.g., deduplicate, prioritize, budget, compact, assemble), the token-budget cap with its compaction threshold, and the policy for re-injecting critical constraints after compaction.

3. Invariant register — every invariant with its statement, source requirement ID, enforcing component, verification method, and an operational fallback if it is ever violated (a concrete action, not “fix the bug”).

4. Trace matrix — every requirement mapped to its enforcing component, its test/evidence, and its runtime monitor.

5. Memory/state design — what state survives across sessions, interruptions, and versions; write and retrieval policy; ownership; retention; privacy.

6. Permission model — file-level read/write rights for each AI coding agent’s role; default is no read, no write; every path is explicitly whitelisted.

7. Runtime policy catalog — what the system does when each degraded or failure path is triggered.

8. Candidate evaluation table — the comparison that justifies the chosen architecture.

9. [optional] Evaluation logbook — the accumulated evidence behind the architecture choices.

10. [optional] Risk list — assumptions that could become defects, with review triggers.

11. [optional] Option ledger — rejected architectural options and when they should be reconsidered.

## D3 — Coding Governance

Produce the governance files that control how the AI coding agent plans and builds the application:

`AGENTS.md` (at the project root directory) — the single entry point the coding agent reads. It declares the build target, the reading order for architecture artifacts, the code baseline, what is readable/modifiable/frozen, the module organization, the integration contracts between modules, and the verification requirements that the generated code must satisfy.

`docs/code-governance/structural-constraints.md` — module organization rules: each architectural element maps to exactly one module; new work extends the existing baseline, never replaces it; every module and function references the architecture decision and invariant it implements; authority boundaries.

`docs/code-governance/mcp-tool-manifest.md` — the tools the coding agent may call, and which roles may call them.

`.opencode/permissions.jsonc` — the project-level permission model in machine-readable form, with guard rules and enforcement mechanisms.

`.opencode/rules.md` —the project-level always-on behavioral rules for the coding agent. Humanonly file.

`.agent/rules.md` — the project covenant: abstraction limits, dependency constraints, test independence (at least one negative test per feature), the rule that changing safety-critical code requires an architecture decision and human approval, and context freshness (rules updated within one sprint of a requirements change).

## D4 — Verification Governance (as markdown .md files)

Produce the verification rules that the verification agent applies, and the QA records the team maintains:

`docs/code-governance/verification-constraints.md` — every fit criterion has at least one test; every invariant has at least one test that fails when the invariant is violated; every test references the requirement or invariant it verifies; every new round of work runs all previous rounds' test suites with zero regressions.

Verification is three-tiered: structural (imports, module boundaries, permissions, architectural fitness functions), regression (all prior suites pass), and behavioral (quality thresholds such as faithfulness/relevance scores, zero safety escapes).

`docs/review-memo.md` — a review memo per pull request, covering spec alignment, architecture alignment, code and test quality, and operational metadata, with security and efficiency checked throughout, ending in a verdict of APPROVE, CHANGES REQUIRED, or REJECT.

`docs/debt-register.md` — technical debt tracked across the AI-era categories: prompt rot, hallucinated dependencies, untouchable code, hidden dependencies, agent-induced bloat, evaluation debt, guardrail debt, and human/cognitive debt.

`docs/bug-diary.md` — a diary entry per significant bug: symptom, reproduction, classification, root cause, fix, and which invariant gap it exposed.

## D5 — Agent Session Transcripts

One full, raw transcript of an AI coding agent session to build the system implementation from scratch. Each transcript is annotated with the student team members' marked interventions and a rationale for each, showing where the team interrupted, redirected, approved, or rejected the agent's work. Collectively, the transcripts must demonstrate the entire supervised pipeline: requirements classification, architecture candidate generation and evaluation, plan approval before code, build, verification compliance, and architecture revision based on test evidence.

## 6. Blocking-Gate Requirements (D7)

The CI/CD pipeline must implement the following blocking gates.

1. Test approval gate — no code change merges unless the tests for the change were approved before implementation began.

2. Static analysis gates — lint, type-checking, and dependency checks run on every commit; contract, security, API-surface, and permission checks run on any pull request touching safety-relevant paths.

3. Schema gate — the requirements registry validates against its JSON schema.

4. Semantic evaluation gate — for any prompt or model change, the pipeline replays a fixed evaluation set against quality thresholds before the change can reach production; if a threshold fails, the change is blocked and reported.

5. Regression gate — every change runs the full prior test suites; any regression blocks the merge.

6. AI-use log gate — a pull request that changes code or prompts without updating the AI-use log is blocked.

Branch protection: Branch protection must require passing CI, and changes to safety-critical paths must require human review with an accompanying architecture decision.
